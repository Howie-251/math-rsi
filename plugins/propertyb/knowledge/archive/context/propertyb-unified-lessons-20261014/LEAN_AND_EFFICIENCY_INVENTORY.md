## 1. 已能固定复用的 Lean 接口

复用应按声明的量词和假设判断，不按目录名称判断。下面一些接口位于 `ThirtyFour/`，但并未写死34边或21点；它们可以直接供后续边数使用。除特别注明，超图层当前仍使用 `Simple5Hypergraph (Fin v)`；数学机制可能推广到一般一致度，但不能把未改写的代码称为已经形式化一般 k 元超图。

## 2. 正确性验证应覆盖哪条链

### 2.1 分清三个相互独立的数学义务

首先是原对象一定能产生要处理的输入；其次是所有这些输入都被分类或证书覆盖；最后是证书所算的数确实推出原对象的结论。分别写成：

`任意原 H → 一个实际库存/配额 → 已覆盖输入 → 染色见证`。

只证明 `Certificate H → PropertyB H`，只算每个保存的代表都严格，或只证明 `Target34 ↔ RemainingGoal`，都只完成其中一段。后一种等价非常有价值，因为它能准确暴露剩余义务；它本身没有提供 `RemainingGoal` 的证明。

**可执行规则：** 一个分支在进度中计作闭合，必须有接受该分支实际 H 和数学分流条件、返回 `PropertyB H` 的导出声明，并已接入所需下游。目录、数值、选点等作为支撑成果单独报告，不折算成“定理完成百分比”。这个规则并不否定条件引理的价值，而是防止交付层级混淆。

### 2.2 完整分类要证明什么

先从实际对象推出有标号输入的完整范围，再用显式置换送往代表。对称代表的合法性、代表数和两两不等价，都不能单独证明覆盖。

T33 的例子：三低完整有标签域是1796；844只属于规范低预算子域。六锁611是最大 pair 预算下的完整可行大迹族，不是611个“极大族”，更不是243代表的同义数字。T34 的例子：21点至少五七度分支有3618个容量分配，其中1993满足实际输入其余条件，再进入严格五锁或同一 H 的四锁投影。23点3→4的460/167容量分配、246/66正共度输入、73/48轨道，也是三层不同对象。

**可执行规则：** 每张表只需写清对象、标签约定、数学容量、覆盖声明和实际调用；不建立额外通用评分系统。剪枝必须以“所有实际输入满足此条件”为依据。压缩模型里的反模型可以说明信息不足，但未满足原超图全部条件时，不是原定理反例。

### 2.3 有限计算的正确角色

在这里，可接受的正向证明是一般约化与结构论证，加上已证明覆盖的局部类型和精确有理数公式核验。完整性与实际输入对应也在 Lean 依赖链内。整张超图搜索未命中、随机样例、求解器 UNKNOWN 不能代替这条链。

数值探索宜先做一种不同表示的低成本复算，优先发现有序/无序、重复次数、索引和分母问题。例子是固定公共点的联合计数：N=5、左右各2槽、两条二元边共中心时，120排列中8个成功，即1/15，能区分错误的额外 r·q 因子。两个实现算出相同结果仍只是算术证据；之后照样要连接真实输入。

### 2.4 最终核验是指定声明，不是“整个项目看起来编译过”

本项目默认 `lake build` 的目标仍是旧 Main。后续验收必须显式构建所需新主模块，再用原始有限顶点集、五元 Finset 边集、边数上界复述原 Bool 染色，检查实际定义体、导出类型及传递公理。

现有允许的信任基础为 `propext`、`Classical.choice`、`Quot.sound`；禁止项依本项目合同，不把它升级成所有 Lean 项目的通用规则。字符串扫描无 `sorry` 不能代替指定定理的公理输出；只有标准三公理也不能代替命题对齐——`P → P` 同样可以只依赖标准公理。

一次本机增量导入、干净重建和另一人独立复现要分别报告。T33 最终1138-job总装配约12.5秒，因为依赖早已核验；不能用此数字估计新证明从零形式化只需十几秒。正文/HTML的陈述还须对照已证结果，Lean不会自动认证另一份文档每句话。

## 4. 已实测有效的 Lean 效率改动

### 4.1 先改变表示，再调资源

21点七度四锁的首个整块覆盖退出137；拆成64个声明后仍超过15分钟、RSS观测约8GB，被执行者主动终止。数学域是674个局部型与70代表。

随后15552项大数组在数据 elaboration 约84秒时栈溢出、退出134，尚未进入覆盖。最终只保存673个非默认键的 `List.lookup` 关联表，同一完整域的数据 r23总4.22秒通过；完整 kernel r24总87.75秒、峰值约8.12GB通过。见[原性能记录](../propertyb34/round01/middle-lean/PERFORMANCE_NOTES.md)与[成功日志](../propertyb34/round01/twentyone-lean/build-quad-kernel-r24.log)。

**规则与边界：** 不对稀疏大 Nat 编码生成巨量数值 pattern match。小而紧凑的域可试数组；本例数组失败而稀疏查询成功，所以没有“数组必快”的结论。选择一个非平凡真实分类核验试跑，记录实际阶段、耗时和内存再推广。旧运行未完成，不编造精确加速倍数；也没有隔离所有变量的受控性能实验，不把模式匹配写成已唯一证实的根因。

### 4.2 数据、昂贵证书、便宜分派、实际调用分层

925项唯一七度证书模块152秒通过，峰值约10.74GB；3618项多七度证书357秒、整个调用360.32秒，峰值约8.99GB。随后分派和实际 wrapper 修正只需约1–2秒，没有重跑这些证书。见[最终报告](../propertyb34/round01/FINAL_30_MINUTES_REPORT.md)、[多七度构建日志](../propertyb34/round01/twentyone-lean/build-many-r38.log)。

**规则与边界：** 生成数据放 Data；昂贵有限等式放 Certificates/Numeric；全域索引拼接放 Kernel/dispatcher；实际 H 到表再到染色放 actual caller。依赖关系须使轻量接口错误不重复昂贵工作。数学输入或公式变了，相关依赖仍必须重验；模块分层不是跳过重建的理由。没有重计算问题的短证明无须机械拆四份文件。

### 4.3 抑制非必要展开，用抽象参数连接实际量

唯一七度的 actual caller 曾在符号化分配上反复展开 `Matched values`，耗尽 heartbeats。显式标注中间证明类型、局部设置 `Matched` 不透明，并在确需的分支显式展开后，避免无益 elaboration。随后把分派抽成 `values : List Nat` 为参数的 helper，再代入真实库存，避免内核对符号目录深递归。最终 caller1.7秒、wrapper1.5秒通过，标准三公理不变。

**规则与边界：** 当第一条有效错误显示 elaborator 正在展开与目标无关的大定义，先切断这次展开，保持清楚的定理接口；不要第一反应调高 heartbeat。`irreducible` 调整属于 elaboration 策略，不是新增逻辑信任；需要展开处仍须真实证明。

### 4.4 剪枝必须带完整性，分块必须接回全域

容量递归之所以可复用，正是 `BoundedAllocations.mem_enumerate` 和 `PromotionCatalog.actual_mem_of_old` 把实际输入保留下来。纯 Python 提前删除大量输入而没有这个连接，只是更快的探索程序。分块时须用列表拼接、商余或其他明确方式覆盖每个索引；64只是当时有效块大小，不是跨机器最优常数。

### 4.5 并行的是不同义务，重型构建按资源串接

实测单个内核任务已可占8–11GB。数学推导、反例攻击、源码实现可并行；正规重型 Lean 构建由一个执行者排队，避免共享重依赖反复核验及内存竞争。在证书运行时，其他人可清理不依赖该结果的 caller/API 源码，不必全体等待。

这不是所有任务都应单线程的理论。若资源允许、依赖独立且已测吞吐，再增加并发；当前证据不支持“代理越多完成越快”。代理交付必须给命题、实际 caller、模块所有权和最后有用的错误/日志，而非只报“完成若干文件”。

## 5. 一个值得继续做、但尚不能写成已实现加速的方案

25点九锁的数值系数只依赖行位置几何及残余大小，不依赖该 profile 的具体重数；固定 N=16 时只有17种锁定位与16种自由位几何，理论上最多1376个 A/B/C标量可复用。11,692个q=5保存输入中11,334使用五个bare布局，另358使用搜索保存的布局。

[成本分析](../propertyb34/round01/high-math/TWENTYFIVE_FORMALIZATION_COST.md)已给出分组恒等式与精确对角扣除；[探针](../propertyb34/round01/high-math/TwentyFiveCoefficientProbe.lean)及[r4日志](../propertyb34/round01/high-math/TwentyFiveCoefficientProbe-r4.log)已检查系数不依赖重数、线性/二次和重写、对角恒等式和一个**带明确剩余行恒等式/严格界前提**的实际 H 调用。

尚未实现的是按33几何分组的通用 `cached_rows_eq`、公共系数整表、整数缩放证明及11,692输入的正式批量核验。q=5的358个修正见证还须从保存固定布局恢复曾被导出器删掉的配额乘子与扣除；无需重跑位置搜索，但仍是实际工作。bare C的残余大小分组也不能自动分组避锁quota罚项。

**建议的最短下一步：** 证明分组恒等式→验证小公共系数表→拿一个保存的非平凡bare实例跑到实际染色→测端到端时间→才批量导出。若修正调用仍贵，单独定位其真实槽罚项，不把bare优化外推为所有修正都已提速。此方案很有价值，但目前没有代表性数值完整调用的性能对比，不宣称已经实现多少倍加速。

## 6. 为什么此前低估耗时，以及如何改变估计

此前把“数学路线已写齐”与“只剩Lean装配”压得过近；分类完整性、真实库存恢复、标签运输和实际配额，往往各自就是完整形式化义务。局部数字表在 Python 很快，不代表对应核验在 Lean 中同样快。模块数不断增加，也不保证主定理的未闭合依赖在缩小。

当前21点就是直接证据：r=2仍缺完整565输入分类、99代表扩展和实际两匹配矛盾；r=3仍缺1722代表分类、共同单位选择、67扩展和矛盾；r=4已有16项pilot，但并非其1993单布局加7联合见证已全部形式化。[接口缺口报告](../propertyb34/round01/twentyone-lean/SEVEN_R234_INTERFACE_GAPS.md)详细列出了现存接口。22–25还有各自完整分类/实际染色。说“再一次总build就好”会误导时间预期。

下一轮估计应建立在已有义务图而非主观完成百分比：

1. 明确哪个实际分支的公开声明将闭合；把仍欠的选择、覆盖、精确界、实际恢复和装配列在同一行。
2. 为新的重表示跑一个有代表性的完整 caller，而不是只跑数据文件或一个最容易算的表项。分别记录展开、核验和接入的实际成本。
3. 只有结构/接口都已试通，剩余确为同型已测批次时，才据实测给粗略区间；尚未实现的通用桥、联合矛盾或未知内核成本应明确列为未定项，而不是猜几分钟。
4. 并行估计看依赖链和实际资源；排队的重证书不能全部除以代理数。每当变化会影响关键链，更新预计，避免固定时间承诺反复顺延。
5. 阶段结果以缩小后的 `RemainingGoal` 和无条件分支 `PropertyB H` 声明报告。源码、表行、模型赞同和纸面齐全分别写，不混成一个“快好了”。

这不要求增加仪表盘、通用调度平台或定期机械评分。维护已有 `PROGRESS.md`、最后有用的构建日志及一个清楚的下一义务即可。此次最终半小时确实闭合了两个真实21点分支，应该直接认可；它也清楚显示剩余不只半小时，按用户时限暂停是准确的收卷。

## 7. 跨模型审阅怎样提高有效信息

让 Grok/Gemini处理具体负重义务：独立反译定理类型；在原始对象范围找新引理反例；检查实际H如何进入局部表；核对置换方向、空迹、对角项或配额交叠；最终审原导出定理及公理输出。不要只问“你同意了吗”。

二者不同结论由实际推导、见证或源码核对决定，不投票。它们曾把无放回联合抽样写成独立抽样、把未分配自由点排列数记错；主代理必须保留正确公式并纠正文案。当前promotion审阅只覆盖指定通用接口与23点首步；没有运行Lean，也不覆盖21点新总装配或最终T34。见[审阅处置](../propertyb34/round01/reviews/REVIEW_DISPOSITION.md)。

同家族意见标为provisional，跨家族有效返回也只是对应范围的审阅证据。对新结构/新接口审阅一次并解决具体疑问；数学和接口未变时不为凑轮次反复付费。网络失败按已有授权处理，不记作通过，也不阻塞不依赖该审阅的工作。
