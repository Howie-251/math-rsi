# 从 aris4math 提炼的 ARIS Lean 工作流

建议新增一个 **`lean-formalize`** skill，将“数学命题→完整 Lean 主定理→可复现查验”作为它的专门职责。现有 `proof-writer`、`proof-checker`、`proof-orchestrator` 已覆盖推导、审计和持续研究；Lean 技能补上实际形式化与完成判定，不另建一套研究框架。

当前产物是[可阅读的技能草案](../aris-skill-drafts/lean-formalize/SKILL.md)与[核验及交接参考](../aris-skill-drafts/lean-formalize/references/verification-and-handoff.md)。它们保存在本项目，没有修改 ARIS 上游、全局技能安装或现有 reviewer 路由。

## 最值得固化的经验

本项目早期已有大量通用引理和数值声明编译通过，原目标却仍只是定义。真正完成的步骤是把实际超图、类型重数、真实排列事件、严格界与原染色见证全部连起来。因此完成条件必须落在**原始命题的实际证明**上。

| 环节 | 应产出的依据 | 本项目暴露的误判 |
|---|---|---|
|固定规格|明确对象、量词、原假设、结论，并对应 Lean 定义|把内部点对覆盖、顶点数范围误加到原目标|
|局部推导|明确引理及其调用条件|看到某个分数小于1就宣称证明完成|
|实际输入连接|从任意输入构造出引理要求的对象和前提|把 profile、概率界或类型实现留成待用户提供的参数|
|整体装配|主定理消除所有内部条件，返回原结论|只完成约化或单个分支|
|机器核验|显式构建 Main、另行导入、展开声明、打印传递公理|默认 `lake build` 只编译了定义所在的根模块|
|独立查验|具体数学义务审阅、实际复现日志、范围明确|把多模型赞同或读取日志称作独立重建|
|交接维护|可读证明、完整源码、锁定环境、下一步或完成状态|把本机路径和缓存当作可移植材料，或复活旧缺口|

## 建议与既有 ARIS 技能的配合

```text
research-lit / research-wiki
          ↓  原题、相关定理、反例与来源
proof-writer / formula-derivation
          ↓  显式论证与关键义务
lean-formalize
          ↔  proof-checker / research-review / auto-review-loop
          ↓  原主定理 + 命题对照 + 构建与公理证据
research-wiki 更新 + render-html + 人工查验交接
```

已有数学证明可直接进入 Lean；已有 Lean 项目从剩余义务继续。各步按实际需要使用，不要求每道题把所有技能跑一遍。`proof-checker` 的现有论文审计角色和输出格式保持原样，Lean 证据可以成为其审核依据。

## 跨模型审阅怎么嵌入

本项目已授权 Grok 和 Antigravity/Gemini，可继续用它们审查具体问题。可迁移技能应使用当前可用、已获授权的 reviewer，不能把特定厂商、型号、额度、代理或重试次数写成所有用户的前提。

最有价值的时机是：最初命题对照、新增关键引理或实质修复、最终原定理装配。每次交给 reviewer 的应是需要判断的实际公式/源码与问题，例如“这一定义究竟表达什么”“这些假设在哪里被提供”“是否存在反例”。失败调用、同家族意见、跨家族意见、亲自执行构建分别记录。没有具体新问题时结束循环。

## 计算与证明的边界

可复用原则是“证明覆盖及语义对应，再使用经核验的计算”。本项目用户要求不以整图枚举作为最终路线；这应保留为项目约束，不能推广成所有形式化项目都禁止穷尽计算。合法有限证明、经验证的证书和一般定理可以组合；有限样例没有覆盖证明时，只提供测试证据。

同样，不把本项目实际出现的三个标准公理当成每个证明必须恰好出现的名单。要核对具体声明的传递依赖及任务允许的信任基础。编译器支持的计算涉及更大的信任范围，需按固定 Lean 版本判断并如实记录，不能为了消掉报错而悄悄扩大。相关机制见 [Lean 官方参考](https://lean-lang.org/doc/reference/latest/)及[社区维护的说明](https://leanprover-community.github.io/extras/pitfalls.html#native_decide)。

## 用多大的文件结构

第一版只需要一个技能入口、一份条件读取的核验参考及 Codex UI 元数据。沿用项目已有的规格、证明义务表和交接文件，不增加新的状态数据库、调度服务或“万能证明器”。只有出现重复、具体的执行需求后，再考虑加 helper。

准备贡献到 ARIS 时，需要同时落到 `skills/lean-formalize/` 和 `skills/skills-codex/lean-formalize/`，按各宿主调整工具调用；补目录与相关技能入口，并运行仓库现有一致性检查。草案当前没有硬编码 `spawn_agent` 型号或 MCP 工具路径，便于保持两份语义一致。

## 当前验证范围

技能结构验证和隔离行为检查的结果保存在 [skill-evaluation/lean-formalize](skill-evaluation/lean-formalize/)。两个测试源码均在 Lean 4.24.0 实际编译通过；独立测试者正确区分了仅证明 `Target → Target` 的情况与真正证明 `Target` 的情况，也没有把模拟的失败 reviewer 调用记为有效意见。测试指出的小型单文件边界已修正：直接编译并打印类型、公理可以提供相应核验，不强制另建工程。缺少额外交接核验不等于数学上缺少证明。该技能的通用效果仍需后续不同数学项目检验；本项目的一次成功不证明它可以解决任意难题。
