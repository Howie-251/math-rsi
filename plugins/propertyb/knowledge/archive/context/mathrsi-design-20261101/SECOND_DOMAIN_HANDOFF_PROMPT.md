# 给第二领域 agent 的交接请求

下面正文可直接转发。目的：依据两个真实数学领域的研究经验，提炼可复用的 `mathrsi-base`，并明确领域插件的接口与职责。

---

请在你负责的项目中，整理一份 `MATH_RSI_DOMAIN_HANDOFF.md`，供另一个 agent 阅读、核对和提炼跨领域数学工作流。你负责本领域的事实与经验；对方负责与 Property B 项目的经验对照，提出 base 与插件的边界。

先按本领域实际研究过程独立整理。可以提出架构建议，但请把事实与建议分开，保留与预想通用流程不一致的地方。当前已有一个 base／plugin 草案，后续会用于对照；这轮不要求你的领域迁就该草案。

优先复用已有 wiki、交接、证明、代码与日志。整理本身不改变正在运行的 Goal、研究方向或程序，也不需要重跑昂贵验证；缺少的证据如实注明。仅在你的项目内保存交接文件，不修改另一项目或 ARIS 核心。

## 1. 先告诉读者怎样读

开头用一页以内说明本领域在研究什么、哪些结果已经完成、目前主要缺口是什么。

随后给一份精简阅读地图，按“必读 → 按疑问深入”排列。每个入口写出：

- 文件路径与对应章节／函数／定理；
- 它回答哪个问题，为什么值得读；
- 它是当前规范、原始证据还是历史记录；若已被后续结果替代，指向现行入口。

优先提供足以理解目标、主要方法、验证边界与效率问题的少量材料。大目录给定位线索，不要求对方先读完整聊天和全部日志。如果跨项目读取受约定限制，可以在独立交接目录提供必要摘录与来源位置。

## 2. 原问题及验收逻辑

写清数学对象、量词、参数、目标与允许依赖。说明完整解答可以是什么：证明、显式构造、反例、完整排除或其它任务指定的产物。

如果有 verifier，说明它读取什么、实际检查什么，以及哪些内容仍需另外证明。例如：候选本身的合法性、目标值、分类覆盖、归约无损性、外部文献依赖，分别由什么保证。没有自动 verifier 的部分直接指出。

区分已完成的原命题、条件引理、局部排除、计算候选与探索未命中。状态以实际记录为准。

## 3. 真实的解题路线与转折

选择最有代表性的成功和失败案例，尤其是这些情形：

- 一项归约、表示变化或通用引理，使原来昂贵的工作明显减少；
- 局部搜索持续很久却没有推进完整目标，后来换路或明确停止；
- 有些计算虽大，但覆盖清楚、成本可接受，实际比继续追求理论压缩更有效；
- 验证曾发现候选错误、覆盖遗漏、原题与局部结论断开，或提出了关键修复。

每个案例交代：原先卡在哪里 → 当时知道什么 → 做了什么改变 → 实际结果 → 剩余限制，并附最直接的证据入口。有实际 CPU、墙钟或 token 记录就引用；没有就不要补估成实测数据。保留尚未解决的案例及有价值的条件成果。

## 4. 本领域需要怎样的插件

描述可以复用的数学对象表示、引理与归约、策略、搜索器、计算程序、独立检查器和知识库。指出各自适用条件与常见误用。

重点回答：

- 通用调度者要给你哪些信息，你才能提出下一步有价值的行动？
- 你能向调度者报告哪些瓶颈和进展证据？如果没有统一数值指标，怎样用具体数学义务表达？
- 哪些决定需要领域数学判断，不能由通用流程依据一个分数决定？
- 哪些机制属于项目偏好或单题要求，不能固化成所有数学任务的规则？

可以给一个本领域真实的“输入义务 → 建议行动 → 结果与范围 → 下一步决定”例子。只提供已知的运行事实，设计中的接口明确标为建议。

## 5. 用过哪些 ARIS 能力，以及哪些环节仍靠 agent 判断

按实际使用记录列出有帮助的 skills／subworkflow、wiki、外部模型讨论和委派方式。区分已经使用、只读过、以及建议以后使用的能力。

说明它们在哪个具体环节起作用，是否存在不适合本领域的默认假设。没有记录时写明，不为了覆盖技能清单而补造使用历史。

## 6. 给 base 提炼者的意见

最后分三类列出简短建议：

1. 值得进入通用 base 的流程机制及其案例依据；
2. 应保留在领域插件或单题工作区的知识与政策；
3. 尚不能判断，需要另一个领域对照或小规模实测的设计问题。

如有适合后续验证工作流的历史断点或新义务，可给入口，并说明复放时哪些材料是后来才获得的，避免把最终答案提前交给 agent。这里只推荐候选，不启动复放或新研究。

最终给我交接文件路径，以及最值得另一个 agent 先看的几个入口。详细证据继续复用原文件，正文讲清因果与衔接即可。
