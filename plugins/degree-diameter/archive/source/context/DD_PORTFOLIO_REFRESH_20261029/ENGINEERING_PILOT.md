# 有限工程价值诊断：保边增点真的改善了什么？

状态：**建议任务，尚未执行**。主目标仍是数学构造；本试验不自动成为独立长期Goal。依据来自项目已保存扩张对象，以及Slim Fly、Jellyfish、PolarFly对网络设计的研究动机，见`SOURCES.md`。这些论文没有替本项目验证工程收益。

## 1. 首先不要混淆三件事

图的阶数增加 ≠ 可接服务器数增加 ≠ 吞吐或延迟改善。图中一个顶点若代表交换机，它的网络度数只占总端口的一部分；服务器端口、链路速率、路由和负载必须另行规定。

已有三族保持旧边，对旧顶点距离不会变坏，但流量路径可能重新集中，旧端点注入能力也可能被新网络边占用。这里只提出待测问题，不预判坏或好。

## 2. 第一项先做端口账本（本包给出推导，不含实测收益）

假定所有交换机总端口数均为r，且每条交换机间无向链路占两端各一个端口。n点m边图的潜在端点槽位总数是：

    P = rn − 2m.

增加a个交换机和b条网络边，则 `ΔP=ar−2b`。异构设备用 `Σr_v−2m`，新旧r保持可比。这个公式只是空闲槽位上限，不保证这些端口都能接服务器、满足供电或提供足够网络吞吐。

由交付和保存序列可得下列输入（不是本次重新验图）：

|扩张族|新增交换机a|新增网络边b|潜在端点槽位变化|
|---|---:|---:|---|
|(11,5)|3|33|3r−66|
|(12,5)|60|720|60r−1440|
|(13,5)|40|412|40r−824|

不能默选最有利的r来证明工业优势。若暂时没有真实设备目标，用r的符号式或明确标注的几个假设值作敏感性分析，不声称对应当前商业硬件。

原先空位如果已接服务器，保边新增链路并不等于保留所有服务器连接。要说明连接名额是原本预留的还是需要断开已有端点。

## 3. 最小试验对象与公平比较

先自主选三族中的一族，比较原公开完整源、一个中间扩张、项目最强扩张。可优先资料最齐全的一族，不要求三个都跑。先复用已有生成器和对象，避免在尚无价值假设时恢复另一批巨大基线。

区分两项不同试验，不能合成一个“优于原图”的分数：

- **旧业务保持**：同一批旧端点、相同需求矩阵和注入量，观察新增设备后是否改变链路负载或可达性。要保证旧端口分配合法。
- **扩容收益**：添加明确的新端点并计入新增交换机、网络边和端口成本；在相同链路速率与路由模型下比较可承载需求或每端点资源。不能拿更多设备直接对比更少设备后说单位成本更低。

若主张优于其他拓扑，才进一步加一个端点数、总端口预算与链路容量匹配的基线。不同规模无法严格配平时说明差异和控制方法，不直接画一个混合排名图。

## 4. 首批只需回答一个性能问题

先选择明确路由，例如固定最短路，或逐跳在所有距离递减邻居间等分的理想ECMP。若还使用“所有最短路径均匀分流”，要说明它与逐跳ECMP不是同一规则。

选择一到两类明确负载：固定旧端点的均匀需求、已登记的随机置换负载，或可重复的热点负载。定义链路容量按有向弧还是共享双向计算。固定随机样本和重复次数只为复现，不以样本未发现坏行为推断所有负载都好。

最初报告：

- 端口/端点账、保留/新增/删除的链路数及设备增加；
- 路径跳数分布、最忙链路负载和负载分散度；
- 在固定理想路由与容量模型下允许的需求缩放倍数及其定义。

上述缩放倍数不是实测吞吐；平均跳数不是实测延迟。没有排队、包长、拥塞控制和硬件延迟模型，不作相应性能主张。算法成本高时可抽样业务作诊断，但标明抽样范围；数学直径仍用严格证据，不用抽样代替。

容错可在有具体疑问时追加有限故障试验，说明随机/定向故障选择。样本中的最坏表现不是所有故障的严格最坏界。没有布局数据不报线缆长度、成本或能耗优势。

## 5. 什么结果值得继续？

支持：在公开的合理假设下，保留端点服务并实现额外规模，或者以可量化少改线代价达到预定性能；结论仍限于所测规模、路由和负载。

反例：端口净增不成立、某类负载明显拥塞、收益依赖不公平预算。反例应指导改邻域选择，或说明这项工程路线暂不值得投入，不隐去负结果。

不确定：只有跳数改善、没有端点/成本绑定；或者样本不足。应标成有限诊断，不能升格工业贡献。

只有首次诊断显示明确问题或价值，才考虑更细仿真或系统论文路线，并与用户讨论新的投入。不要自动安装大型仿真平台、采购硬件、搜索产品或恢复旧D2开放任务。
