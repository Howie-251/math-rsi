1. 哪些已经能直接复用

MathRSI 已经把 prepare、route-loop、prove、verify、handoff 的输入、返回、消费方和回流写进实际 SKILL。其插件接口是 agent 可读的 Markdown 调用契约，而非自动注册的 Python 插件系统。

对应关系：
- prepare/survey：恢复原参数与目标，查公开构造、论文条件、作者补充和基线。
- route-loop：围绕当前覆盖障碍形成路线，安排有信息的预测、受控修改和探针。
- prove：执行结构推导、生成器与有限搜索，回收代理的实际结果。
- verify：接现有图检查器，核当前见证或特定数学义务。
- handoff：整理构造说明、证据、结果表、HTML 和恢复入口。

Wiki 原位复用、局部验证返回原调用处、共同对象约束、代理独占写入、及时回收完整产物、UNKNOWN 不等于不存在，这些都已有明确支持。不要把它们重新包装成另一套冲突计划。

2. 建议新增一个有实质内容的 Degree–Diameter 插件

建议组织为一个领域入口和两项可独立工作的能力，名称仅为建议，当前仓内尚不存在：
- mathrsi-degree-diameter：明确图类型、最大度/正则性、直径要求、参数选择、公开基线及已有知识入口。
- dd-construction-lab：提供完整适用条件、路线覆盖解释、生成规则、实际程序、有代表性的成功/失败案例与继续理由。
- dd-certificate：读取具体见证，核简单无向图合法性、点数、最大度和直径；解释对称性代表根、归纳证据或全源检查分别支撑什么。

本地试接可以调用现有工作区的程序。若作为可分发插件，必须收入所需的真实推导、生成器、检查器和可运行案例，不能只留作者机器的路径表，也没有必要搬入多年全部日志。

最适合先收入的具体知识是已有保边扩张规则：
对合法图 G，保留全部旧边，只新增一个点 z 及 z—S 边时，需要
S 中旧点都有至少一个剩余度数，|S|<=Δ，且
    union_{s in S} B_{D-1}^G(s) = V(G)。
它解释了为何覆盖成立、为何满度源没有这种接口，以及为何每次必须检查当时的完整图，包括此前新增点。这是已有知识的迁移，不是本次新数学成果。

若删除旧边，旧点之间距离的原保证就需要重新处理。控制器/代数构造则应保存实际路线与共享参数的兼容条件，不能只留下点数和度数公式。

3. 我们能贡献给通用框架的两项经验

第一，把“直觉”落实为可被推翻的预测，并让实测改变下一步。
不能只说某方法有希望；重要实验应说明预期修好哪类点对、保住哪类覆盖、哪项共同约束可能失败，随后比较预测与结果，决定改生成规则、深入或暂停。它不要求每次另建 PRED 文件。

MathRSI 已有有界探针和信息增量判断，可以补入我们更具体的图构造例子，而不把已有原则再登记一次。历史 global256 试验可作例子：路线容量可以通过，同一参数的不同槽仍不能同时覆盖，最终只能关闭准确限定的构造族。

第二，参数开放任务应按“机制＋共同缺口＋适配参数”选题。
我们的任务常常不是固定一个定理，而是从多个参数中找到更有希望的构造。建议首版在 DD 插件/任务约定中表达这种选择；实际试用有价值后，再把适用于其他参数化研究的部分提炼进 route-loop。不要在通用核心固定某些度数、最多几条线、统一分钟数或人为权重。

4. 对图构造尤其重要的结果解释

候选、完整合法图、超过某个已读公开构造、最新公开纪录和方法创新，应分别说明依据。一个表格里的改善不自动等于全球纪录，同一机制的许多参数例子也不自动变成同样多项独立创新。

失败同样保留准确范围：固定族完整排除、有限样本未命中、局部搜索和 UNKNOWN 含义不同。记录实际生成规则、参数域与失败见证，才能避免重复工作。

验证要复用仍有效的证据。保边操作可以继承旧旧距离保证；规则变化后只重新处理受影响的义务。完整见证的结论仍要被充分支撑，但不因为换框架就重验所有旧图。

Lean 在框架中已经是按任务需要接入的能力。某项任务若明确要求最终形式化，就保留该要求；这不意味着迁移时要逐一审读历史 Lean 文件。

8. 后续讨论：框架的必要性与 RSI 优势（2026-11-02补充）

用户进一步提出的评价标准：直接使用 Codex/Claude Code 也能取得结果，因此 MathRSI 应说明知识如何服务新问题、是否能在同一领域持续产出，以及经验积累是否使后续研究更强或更快。下面的判断与前面的“结构上能整合”是两个不同问题。

当前结论：仓库已有实质的领域知识、研究工作流、知识使用实例和经验反馈维护机制；还没有给出同等条件下优于直接使用 agent 的研究性能对照，也没有建立跨任务持续变强或提速的实测证据。

已经体现的部分：
- Property B 知识库保存定义、适用条件、推导、失败反例、程序和来源，具有可复用内容。
- 多个 k 的历史成果和一般 k 定理说明已有方法能用于一系列目标；但这些研究先由 ARIS 完成，再提炼成 MathRSI，不能据此归因于新框架。
- forward-use 试用让另一位 agent 仅凭仓内材料复跑七元130边结果，并诊断131边时新增13类必要输入、旧选点保证失效及两种布局不再严格。它展示了知识接手与邻近目标诊断能力；未解决新的131边目标，未对照不使用插件时的表现。
- EVOLUTION_WORKFLOW 给出从使用证据到实际补丁、审阅、独立试用、采纳的维护路径。开发中确有父子重复调度、局部核验返回位置等修复；已测范围是局部行为或静态消费，不等于持续数学研究性能提升。
- 随包还有 ARIS 的技能触发率评测脚本，测量是否调用了合适技能；协议测试、触发率和已知案例重放均不能直接回答数学解题能力是否提升。

关于“大知识库里抽取求解思路”：值得做，但可用的单位应是带条件的方法、引理和程序。每项经验至少让 agent 找到：解决哪类障碍、需要什么前提、得到什么结论、有哪些失败边界、怎样实际调用及原证据在哪里。新问题需要检索候选后核对前提，并将结果接回自己的目标。仅把相关文字送入上下文，不足以说明数学方法能够迁移。

现有阅读地图、实体关系和恢复机制是起点，跨题检索效果仍需检验。已有试用还发现过“知识成功写入实体，但关键条件没有进入自动query_pack摘要”的具体问题；这说明保存知识与下一次真正用到知识，需要分别检查。

按照本次用户提出的 RSI 标准，可采用这样的可观察闭环：
解决一批问题 -> agent提炼经验并提出修改 -> 更新共享知识/方法/工具/选路规则 -> 用于之后的新问题 -> 在相同条件下表现更好 -> 保留有效修改。

这里可以改进 agent 系统使用的知识与策略，不必先修改底层模型权重。但要说明经验由谁提炼、哪些修改由系统提出、人工参与多少，以及收益究竟来自知识注入、工作流还是持续更新。一次任务内部反复修正答案，只能证明该任务被推进；跨任务共享能力是否提高还需后续证据。

建议先做能区分贡献的四种对照：
A：正常使用的同一底层 agent，拥有平常可用的工具与合理任务说明。
B：A 加同一份领域知识，检验整理好的知识是否有帮助。
C：B 加固定版本的 MathRSI 流程，检验流程本身的增益。
D：C 在先前研究任务中提炼并采纳更新，再在保留的新任务上检验；与停止更新的 C 比较持续改进的价值。

B相对A有收益，支持领域知识的价值；C相对B有收益，支持流程的价值；D相对C在后续任务上改善，才直接支持本次强调的持续自我改进。若某层没有改善，应据实收缩该层的主张，而不是把所有收益统称为RSI。

比较时保持底层模型、工具权限和可比总资源；原始agent对照也能使用正常的搜索、代码和代理能力。分别比较固定预算下的正确结果数量，以及达到相同数学与验收目标所需的时间、模型调用和计算成本。知识整理/维护的前期成本单列，系列任务中的摊销可以报告。更多并发花费带来的墙钟缩短应如实呈现资源差异。

测试任务应与形成经验的任务分开，不把已收录答案的重放算作新问题解决。已知定理直接应用可以单独评价知识调用；新方法探索另列。不要把测试反馈写入库后再测同题，并把这种记忆效应称作泛化。

建议首先在我们熟悉的图构造领域验证这条闭环，选取需要方法迁移的一组可核对任务；得到证据后再扩大知识库与领域范围。当前优先事项是明确“经验如何改变下一次行动”和安排可归因的对照，而不是根据案例数量直接宣布框架更强。

本补充是设计建议与已有证据评估；没有执行上述对照实验，没有新增研究Goal、模型调用或子代理任务，没有修改MathRSI源代码。

9. 后续聚焦：专题库能否服务不叫 Property B 的新问题

结论：框架已经设计了“通用流程＋可扩展的领域插件”，也把部分跨领域经验写入base；当前主要成熟的是Property B专题库。主执行路径尚未充分体现“根据新问题的结构和障碍，从所有专题中主动找出适用方法”的统一知识调用方式。

实际依据：
- plugins/下目前有propertyb和ecc；后者仍是草案，未进入默认技能发现。
- docs/PLUGIN_CONTRACT.md:63明确允许多个插件组合，并要求对象、符号和归约方向对齐，说明设计并不限定只能研究Property B。
- base/skills/mathrsi-survey/SKILL.md:73-95给出的具体领域分支是“属于Property B且插件已启用”时调用其文献技能；其他题走通用research-lit。它具备通用新题调查路径，但这条路径并未明确承接跨全部专题的方法检索、适用条件核对和调用。
- base/skills/mathrsi-research/references/efficiency.md:47-67已从Property B与ECC提炼“各局部最坏值不能任意拼到同一对象”等通用原则。因此不能说完全没有跨题抽象；目前这类内容主要作为通用研究指导出现。

建议先扩大知识的可发现范围，再随实际新题扩大内容。Property B名称可以保留为领域入口和来源标签，但面向新题还需要按“对象结构、当前障碍、目标、适用条件”找方法的入口。单纯改成更大的库名或再增加若干专题目录，不能自动完成这一点。

例如新题只说“几种局部方案各自可行，却找不到同时成立的共同安排”，系统应该能找到Property B/ECC中关于共同变量和相容约束的经验，而不要求用户先知道Property B名称。现有base已有相应原则；仍值得补的是清楚的跨专题索引、相关方法的条件与执行入口，以及到原例/原证明的连接。

这个入口可以先是少量高质量方法条目的索引，并通过现有agent读取、核条件和调用；不要求先增加一个庞大的数据库。条目记录“解决什么障碍、需要什么前提、可怎样操作、有哪些失败边界、原证据在哪里”。特定参数结果继续留在原专题中，通用原则也不冒充对任意数学问题都适用的定理。

前一轮建议的Degree–Diameter插件解决了增加一个领域知识包的问题；跨专题方法入口解决的是这些知识包怎样帮助原本不带该领域名称的新题。两者有关，但不能相互替代。本节仅记录设计判断，尚未实施索引或新检索流程。

二、专题是否过窄
当前MathRSI实用内容集中在Property B，ECC仍为草案，尚缺更广任务上的系统表现。不过不能把已有Property B数学成果都说成单点：case-studies/property-b/README.md:22-38给出对每个k≥12成立的一般定理，另有k=5..12的逐参数结果。它证明相应数学命题覆盖一个参数族，不能自动证明新系统对未见题的研究能力。
该README:7与主README:119明确说明这些研究先经ARIS完成，之后提炼为MathRSI。因此它们是知识和设计来源，不能倒过来当作成型MathRSI已取得的前瞻性成果。也不能由本仓选择的少数案例推断整个Property B或ECC领域规模、重要性或参与人数。
一条参数化定理、一种方法批量产生实例、多种新任务上的成功应分别说明。图的参数格数量可以显示覆盖面，但同公式直接代入得到许多图，不单独证明已经学会处理新的结构障碍。

三、题解完或卡住以后，插件还有什么价值
插件不是仅回放一个答案：propertyb-bound-lab/SKILL.md:8、24-34实际支持给定新k/M的必要域、方法选择、缺口诊断及参数化加强。既有结论可直接调用，方法与检查器可在前提满足时复用，严格失败范围可省去重复工作。
已有forward-use试用真实复跑七元130边预算，并在131边预算定位13个新增必要型、旧选点保证失效及旧布局界不严格（development/propertyb-rebuild/forward-use/REPORT.md:7-11、93-105）。这证明包有可执行内容与诊断能力；它没有解决下一预算，也没有测相对普通agent的净收益。
当旧方法到达边界，插件不能保证继续推进；它应帮助识别边界、尝试有依据的新规则、复用可迁移部分或停止原路线。跨专题主动发现这些可迁移部分仍是第9节的不足。增加插件数量或将旧过程写成技能，不自动产生后续研究价值。

四、难题成果、效率和持续改进分别怎样支持
新且可核对的数学结果可以证明研究产出有价值；同一完整任务的新旧方法成本对比可以证明某项提速；让从前题提炼的知识/策略帮助未参与设计的后续题，并与冻结版本比较，才直接检验持续学习收益。这三项证据不能相互代替。
不必等待新的世界纪录才测效率：在答案不提供给解题者的新任务上，同等资源解得更多，或对同一合法目标更省时间，也能提供证据。若声称开放问题发现能力，则仍需真实的新数学结果。困难程度要由具体未解障碍、准确公开基线或可比基线表现支持，不能单凭点数大、算得久或领域小众。
已有computation-and-efficiency.md:97-109有历史checker/算术成本，REAL_PROJECT_TRANSITIONS.md:17明确其历史转折不证明新工作流通用提速；这些局部时间不能相加成整个研究成本，更不能据累计结果增长推断产出速率上升。
以Degree–Diameter为例，可检验从旧图提炼补点适用条件，能否在尚未用于制定规则的参数/来源图上更早排掉无效方案、选到可行规则并产出完整合法图。保持底层模型、允许资源及验收可比，比较冻结策略与允许积累经验的策略；相同图的不同命名/复验不重复计成果，直接代入与需要新结构的推广分开。投入更多代理、更多算力或后期任务更容易，均不能单独解释为RSI收益。
持续自我改进不要求产出速率无限增加、指数增长或每一题都比上一题快。应展示经验导致了什么可执行改变，该改变在后续问题上产生了什么收益；失败试次与整理经验的成本保留。这里是建议的检验方式，本轮没有实施对照。
