# Math RSI：通用研究流程与领域插件

2026-11-01 · 架构讨论稿。以 ARIS 和 Property B 的实际研究经验为依据；本轮仅整理设计，没有实现新 harness 或启动数学 Goal。

## 1. 建议：稳定的 base、可扩展的领域插件、独立的单题工作区

`mathrsi-base + mathrsi-propertyB` 是合理的拆分。它使同一套研究组织方法可以用于不同数学问题，又允许领域方法持续积累。还应把“单题运行”从插件中分出来：m(6)≥67 的具体预算、未闭分支和日志不应成为整个 Property B 插件的固定状态。

|组成|职责|Property B 中的例子|
|---|---|---|
|`mathrsi-base`|固定任务与验收范围；组织证明义务和依赖；检索、委派、预算、停滞诊断、审阅、装配与交接|要求每个条件引理都有实际输入入口；记录计算究竟覆盖什么；在一条路线长期没有新增事实时重新选路|
|`mathrsi-propertyB`|领域对象、已有定理、可用归约、策略、诊断量、计算与证书检查适配|最小反例、点对覆盖、度数预算、选锁、真实迹、共同坏对、排列概率、类型覆盖|
|单题工作区|本题的原始命题、接受的依赖、路线、当前义务、实际输入与运行结果|给定 k、边数预算 M、必要顶点域、未闭度数分支、复算记录|

base 提供可选的 Lean、精确算术、构造验证等接入方式；领域插件提供所需的数学声明和输入。是否使用 Lean、允许什么计算证明、需要哪些 reviewer，取决于任务要求。Property B 的特定偏好不自动成为所有数学任务的规则。

证据按检查对象分别记录：数学推导、分类覆盖、精确算术、跨模型审阅、Lean 核验与原题语义对齐。它们不能排列成自动升级的单一等级；数值全部通过不补分类遗漏，标准公理检查通过也不补原命题被误写的问题。

**base 不是万能数学裁判。** 它可以要求证据、调度验证和保留状态，不能仅凭字段齐全就判断证明正确。自然语言中的量词、无损归约与覆盖仍由数学推理和审阅核实；确定性验证只接受它实际检查的命题。

## 2. 执行是有反馈的研究循环

建议主流程是：

> 固定原命题与验收 → 检索可复用知识 → 选择整体路线并建立义务图 → 围绕关键缺口做推导／搜索／验算 → 检查实际输入连接与反例 → 继续、换表示或换路线 → 装配原命题 → 最终核验与可复现交接。

独立验算和对抗审阅在关键义务形成时介入；不必等待整篇成稿。Lean 按需贯穿：若接口是否能接回原命题是风险，先写原定理类型和真实 caller，再决定扩展多少形式化。不能一律将它作为最后一道翻译工序。

义务图既容纳同一路线中必须全部完成的子目标，也容纳可相互替代的证明路线。新知识可以使旧路线被更短的证明替代。完成比例不从节点数量或分支数量自动计算。

一次委派应有明确的输入、待证明结论、允许假设、下游用途、产物和预算。主代理负责困难归约、路线选择与最终连接；Sol 等 worker 承担可独立验收的阅读、计算、实现和接口核查。模型推理并发与重计算并发分别安排，避免编译互相争内存。

## 3. 效率应体现在每轮选择什么工作

这里容易爆炸的是候选构造、证明策略、参数分类和搜索表示；这不意味着数学各领域都属于组合数学。我们能直接提炼的是处理这种搜索爆炸的方法。

每轮先回答：**下一项工作将改变哪个尚未闭合的数学义务？** 它可以完成整支、给出能被真实输入调用的引理、证明某段搜索无需再做、找到反例，或定位哪条松弛丢失了关键信息。困难研究允许有界探索，不要求每次都成功。

### 三个真实案例

|问题|实际发生的事|应固化的处理方式|
|重复搜索|固定 profile 与界下，双锁位置的 462／506 个可能性已经完整检查|记录固定条件、已覆盖域和重试条件。相同域换种子不重新启动；新约束或未扫位置可以重启|
|优化无效项|20 点 (7,9) 的一项名义扣除为 10/221，但总界实际下降为零|先看总界当前由哪一项控制，再优化有机会改变它的部分|
|局部表示过松|六元最后 35 点分支扩四锁表未闭合；全图预算与共同选点把难点压到少量配置和两次 51>46|先诊断局部模型是否丢掉共同约束，再决定是否扩大局部枚举|

来源：[失败地图](research-wiki/PROPERTY_B_FAILURE_ATLAS.md) §3、§5；[六元方法沉淀](research-wiki/PROPERTY_B_M6_GE67.md)。它们支持具体设计选择，不是新系统已实测更快的证据。

可操作的执行原则：

1. **先诊断再扩算。** 用短运行估计真实成本，保存最紧／失败实例及其原因；插件报告领域诊断量，base 据此组织下一步。
2. **只细分需要细分的部分。** 已严格且已核验的父分支停止展开。八／九元只对失败双锁父型继续三锁，是现成范例。
3. **失去信息增量时强制重新决策。** 同一卡点连续两轮没有实质新增事实，主代理检查表示、共同约束、目标引理和替代路线。重新决策可以有依据地继续原路线；不能把它变成固定时间后必须放弃困难问题的机械规则。
4. **保留全局视野。** 定期检查整条证明最贵的未闭连接，同时推进独立义务。每轮新结果都应回填到整体路线图，避免只盯住当前局部文件。
5. **比较端到端成本。** 数学归约、实现、分类覆盖、独核与形式化连接都计入成本。证据量较大时，还要考虑存储、文件数量、读回与交付成本；ECC 一个批次留下约125.8 GiB、82万份文件，内核查询耗时并不能代表整项成本。有时小规模完整表比昂贵的对称性运输证明更便宜；能完整、快速核验时就算。
6. **审阅围绕新疑问。** 量词、实际选点、分类覆盖、数值方向和主定理连接值得跨模型讨论；已经解决且没有改变的内容不机械重复送审。

“扩大算力”与“换数学方法”不是预设二选一。需要寻找的是当前任务通向完整证明的较短路径。搜索未命中、某个充分界不严格、必要条件模型有解，都须保留准确含义。

**停止原因要与重启条件一起保存。** 完整覆盖且已有结论的固定域直接复用；因连续无新信息而停止的路线，需要说明新约束、表示或预期信息为何值得再试；仅因资源不足而停止的计算，可在资源与授权预算允许后沿原方法继续，不强求先发明新数学。base 可以在允许范围内重新分配资源，不能自行扩大用户冻结的总预算。

Gemini 修订后的讨论把“退回全局”具体化为可供 Property B 插件使用的三项动作：恢复同一原对象在不同局部视图间的共同约束；用上游选点和整数刚性排除难处理的局部型；先检查一条真实输入到结论的连接，再扩展重型核验。通用 base 负责要求这次重新判断，并为替代路线分配有界资源；具体的守恒量、选点定理和连接由插件提出。其他领域可以提供不同的回退菜单。

## 4. 插件的最小契约

先用现有 Markdown、JSON 和脚本表达，不要求先实现统一事件系统。五类信息足够支撑第一版：

|信息|必须说清楚什么|
|---|---|
|任务|原对象域、量词、允许的终点、依赖与验收方式；单个构造与全域排除分别需要什么|
|义务|要证什么、已有结果与依赖；变换是等价、必要覆盖、充分构造还是仅搜索子族；如何返回原命题|
|行动提案|输入域、采用方法、预期新增事实、实际联合规模、资源预算、停止及重试条件|
|结果|结论的逻辑范围与条件、实际覆盖、未解决部分、证据路径、真实成本；已有与本次新增证据分别说明|
|验证接入|对应的具体义务、实际输入、检查器所验证的属性、同一对象所需的共同坐标／变换信息，以及实际对象→局部输入→原结论的数学连接|

例如 Property B 插件可提交：“当前失败来自同一真实坏对在不同布局里被分别取最坏值；建议保留共同变量，证明一个联合下界；若成立，会同时处理 A/B 两支。”base 不需要内置‘坏对’的公式，但必须把这项工作与 A/B 的实际义务和验证安排关联。

插件负责生成候选，也可以提供检查器实现；检查器的数学含义、覆盖和独立验证不能由作者的一句成功日志代替。若完整检查器尚不存在，应记录具体证明义务并继续研究，不能把所有数学任务都假设成已经有自动 verifier 的题目。

**验证能力挂到具体义务上，而非给整个领域贴“有／无 verifier”的标签。** 同一道 ECC 题可以同时包含单矩阵验距、陪集集合无遗漏、配对拒绝和自然语言归约。每个检查器只支撑它检查的那一项；base 组织足以支撑目标结论的证据组合，不将历史项目的双完整扫描或 Lean 变成所有任务必做的工序。

多次规范化还须检查组合是否保真：各自单独无损，不意味着叠加后仍覆盖原对象。ECC 中，固定三个零标签与后续边际规范化可能使用同一组变换自由度；必须撤掉冲突条件、证明两者可同时满足，或覆盖剩余变换轨道。插件负责这项数学连接，base 将它登记为实际组合义务。

**瓶颈信息必须进入接口。** Gemini 首轮提出的有效加强是：插件除了报结果，还要说明当前阻碍是什么、哪项行动可能改变它，以及哪些观察会影响下一次决策。对数值界，可填活跃项与松弛量；对抽象证明，可填缺失的引理、不可同时满足的条件、接口不匹配或当前未知之处。不要求所有数学问题都变成一个可打分的优化问题。

下面是示意交流，不是已有程序 API 或实际运行记录：

```yaml
义务: 从同一实际超图推出一个足以闭合分支的概率界
当前阻碍: 不同布局分别取最坏值，丢失了共同坏对约束
建议行动: 保留共同变量，检查旧最坏配置能否同时成立
预期信息: 新的联合引理，或证明当前联合松弛仍不够的见证
影响: 决定继续这条概率路线，还是返回选锁归约
预算与停止: 先做有界探针；根据新信息决定是否扩域
```

## 5. 两个循环：解题与改进解题方式

**内层：固定版本，完成本题。** 任务执行期间，领域插件不直接改 base 的源文件，不静默改变原命题、依赖范围或完成标准。第一版通过分目录与明确写入职责实现这一约定；这不是已经部署的强制安全隔离。

**外层：从实际失败提出改进，验证后纳入新版本。** 插件可以建议修改 base；独立的维护／评估步骤比较变更，再决定是否采用。每次评估记录实际使用的 base 和插件版本，让成本和结果可以解释。是否自动采用遵循运行者授权，不额外假定每次都要人工点确认。

改进有三个落点：

- 新选锁引理、共同容量界、失败参数域：进入 Property B 的领域记忆与策略。
- 更好的活跃项诊断、任务拆分、检索、调度或实际 caller 检查：可作为 base 改进候选。
- 某题特定中间文件、一次局部运行状态：留在单题工作区。

领域学习也可以纳入广义的 RSI 研究，但应区分知识积累、策略改进与通用运行流程改进。若插件永远不能提出核心变更，RSI 的演进范围会被不必要地锁死；若它在解题中随意改核心和验收，则无法判断改进究竟来自哪里。

## 6. 用现有 ARIS 做最小验证

已有技能可承担大部分组织工作：`formula-derivation` 固定假设和推导链，`proof-orchestrator` 管理持续证明，`research-wiki` 复用知识，`research-review`／`proof-checker` 做有明确范围的审阅，`lean-formalize` 按需接形式化，`render-html` 做读者交付。它们已有指令和部分 helper；目前还没有因此自动得到一个独立实现的通用数学调度器。

先抽出一份 base 工作流与一份 Property B 插件说明，直接引用现有 wiki、引理和程序。用一个保存良好的历史停滞点检验它能否发现已知的无效扩算；复放输入只包含当时可用的材料，不能把后来答案当成重新发现。这个阶段检查机制是否工作，不据此宣称新问题求解能力。

复放的准备者与执行者区分上下文：准备者选择当时版本的题面、文件和断点，执行者只读取这些输入，不继承当前完整 wiki、最终交接或解决方案。旧目录名与创建日期不足以证明里面没有后来追加的答案。先用一个小而真实的断点检验，无需为此另建庞大的评测平台。

之后在未用于制定策略的任务上比较。需要分别区分：同一 base 加领域插件的收益、同一插件换 base 版本的收益，以及插件积累知识后的收益。保持原命题、验收标准和比较预算一致，记录实际模型与工具。首要结果是完整可验收的解答及其成本；仍未完成时，准确记录已成立的新结果，不把它换算成完成百分比。

要主张通用 base 改进，最终还需不同数学领域的独立任务。小样本用于筛选设计；通用效率与持续自我改进的结论，需要后续实验支持。本轮没有运行这些实验，也不借用或干扰正在运行的编码理论项目。

## 9. 仓库与演进方式

用户已认可：初期用一个 GitHub 仓库维护 `base/`、`plugins/propertyb/`、`plugins/ecc/`，各组件共同处于 `main`；具体修改使用短期分支，多个 agent 使用独立 worktree 与明确文件职责。领域长期积累放在插件目录，不放在长期分叉的领域分支。

插件运行时消费固定核心版本；需要改核心时提出单独变更，核对两个插件的实际调用后纳入新版本。单题 wiki、在途状态与大型计算证据继续留在原研究工作区。目录、版本、ARIS复用与协作细节见 [仓库组织方案](MATH_RSI_REPOSITORY_LAYOUT.md)。这份方案尚未创建远端仓库或迁移现有项目。
