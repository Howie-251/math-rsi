# Math RSI 的仓库、插件与协作方式

2026-11-01。用户已认可的组织方案；目前是设计文件，尚未创建远端仓库或迁移研究目录。

## 一个仓库，按目录划分长期职责

初期建议建立独立的 `mathrsi` 仓库，用 Git 保存版本、GitHub 协作。base 与领域插件共同在主线演进；无需一开始拆成多个仓库。建议结构如下，名称可随首次实现调整：

```text
mathrsi/
  base/                   # 通用工作流、义务与验证接入约定、必要的调度代码
  plugins/
    propertyb/            # Property B 方法、领域记忆入口与程序适配
    ecc/                  # ECC 方法、领域记忆入口与程序适配
  docs/                   # 设计、使用与版本变更说明
  examples/               # 小型可运行任务与完整输入
  tests/                  # 已实现接口的必要检查
```

这只是职责布局，不要求立即为每个目录制造代码。第一版可以由详细工作流、插件说明和少量现有工具适配组成；先接通真实任务，再补确有用途的运行器。

领域插件需要 base 提供的接口；base 不导入某个领域特有的选锁公式、码距字段或固定搜索操作器。插件之间也不隐式依赖彼此的单题状态。多个领域都需要的功能，经验证后可以提到 base。

## 分支用于修改，插件目录用于长期积累

`main` 保存可使用的组合版本。一次具体修改开一个短期分支，例如 `feat/ecc-coset-adapter`、`feat/propertyb-lock-selection` 或 `core/obligation-evidence`，完成相应核验后合回主线。

不把 `propertyb` 与 `ecc` 做成各自长期分叉的分支：那样两边容易复制并修改核心，后续难以比较同一版 base 的效果。两种插件应可以在同一主线版本中并存和选择。

多个 agent 同时改代码时使用独立 worktree，明确各自的文件与接口。worktree 隔开工作文件，不能消除逻辑冲突；共享接口由一个 owner 统筹，合并后检查真实调用。短小、互不冲突的文档工作无需强制增加 worktree。

## 插件怎样推动核心改进

解一道题时，插件使用明确的核心版本，提出方法与行动，不直接改正在用于验收的核心和目标。发现通用问题后，可以提出核心修改，并附上触发问题的实际案例。

核心修改作为单独可审阅的变更：说明旧行为、新行为和影响的接口，在 Property B、ECC 的相关实际调用上验证后合入。如果变更跨越接口与调用方，可由同一协调者组织为配套提交；不要求人为制造无法运行的中间版本。

一次运行记录代码提交、启用的插件、任务规格及实际模型／工具即可解释来源。比较新旧版本时保持原命题、验收和约定预算一致，保留原运行记录。核心更新不自动重跑已完成研究，也不自动恢复暂停的 Goal。

当前这些是目录与维护约定，不声称已有程序强制隔离。等实际需要自动执行修改时，再实现与风险相称的写入边界。

## 研究资料与代码放在哪里

|内容|建议位置|
|---|---|
|通用流程、插件接口、领域适配代码、可复用检查器|`mathrsi` 代码仓库|
|小型测试输入、示例证明、必要矩阵及复现说明|仓库中对应插件或示例目录|
|单题规格、research wiki、在途义务、研究日志|原题工作区：`aris4math`、`aris4math_v2` 各自维护|
|大规模扫描证据、缓存、编译产物|研究工作区或独立数据存储，代码仓库保留说明与定位|
|可共享的领域定理与失败经验|提炼到插件的知识材料，保留原证明与证据入口|

例如 ECC 的一个批次已有约125.8 GiB、82万份文件，不适合随每次代码分支复制。保留可复现所需的实际数据、生成和检查入口；可检查的共享包按具体任务制作。既有证明包和原始证据不因提炼插件而删除或整体搬迁。

插件调用任务工作区的资料时，由该任务配置指定位置，不把作者机器的绝对路径写成插件通用默认值。跨领域阅读须服从各项目授权；能加载两种插件，不意味着可以任意读写另一个研究项目。

## 与 ARIS 的关系

复用现有 ARIS 技能和 helper，说明所依赖的来源与版本，保留署名和许可证要求。研究调度层可以组合 `research-wiki`、`proof-orchestrator`、`research-review`、`lean-formalize` 等能力，无需把整个 ARIS 复制一遍后单独维护。

只对 Property B 或 ECC 有效的方法留在插件。经实际任务验证、对更广泛科研有用的改进，可以另行提交 ARIS 上游。这样 Math RSI 可以独立试验，ARIS 也能吸收成熟的通用能力。

等出现独立维护团队、发布节奏或访问权限等真实需求，再把插件拆成独立仓库；届时显式声明核心兼容版本。当前先用同仓库缩短接口调整和核验路径。
