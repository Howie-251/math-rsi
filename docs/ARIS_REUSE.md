# MathRSI 怎样复用 ARIS

MathRSI 把 ARIS 的研究组织能力用于数学问题：保留 agent 的推理、选路和纠错能力，
由领域插件补充数学对象、归约和验证。优先调用已有技能与 helper，不再实现一套平行调度平台。
复用的单位是一个有明确输入与用途的能力；某个技能存在于磁盘，并不表示当前宿主已经加载或执行了它。

本版开发核读的 ARIS 仓库是
[wanshuiyin/Auto-claude-code-research-in-sleep](https://github.com/wanshuiyin/Auto-claude-code-research-in-sleep)，
实际提交为 `c485faa59a68e51c6575dea67ca57abc7a6a2b9c`。
本页的版本事实来自本地源码读取，不代表检查了此后远端更新。
其中重点参考 `skills/auto-review-loop/SKILL.md` 的解释粒度、恢复、原始审阅回应和修正后再审，
另核读了本机安装的 Codex 版 `research-wiki`、`proof-orchestrator`、`proof-checker` 与 `lean-formalize`。
后者是宿主上的实际安装版本，不能仅由上游仓库提交推断它们已全部同步。

## 先判断需要哪项能力

主技能组织本题的原目标、义务与行动。遇到能由 ARIS 直接承担的工作时，
先读取相关技能，再交给它足够而精简的任务材料。没有必要从选题一路调用到论文成稿。
一个短证明可以直接完成；已有完整证明只缺 Lean 接口时，也不重新启动文献发现或实验规划。

|当前需要|可复用入口|传入什么，取回什么|
|---|---|---|
|把散乱等式整理成可用推导|`formula-derivation`|给原对象、已知式和要回答的问题；取回有假设和依赖方向的推导，不把候选公式自动算成定理|
|写一个具体证明|`proof-writer`|给准确命题、允许进口与既有尝试；取回证明、反例或明确缺口，接到本题相应义务|
|跨轮继续证明或准备手动交接|`proof-orchestrator`|给现有 run、原规格、已审结果与孤立难点；按该技能的运行目录和交接合同继续|
|查已有论文和领域知识|`research-lit`、`research-wiki`|先查本题已有知识，再为具体缺口找来源；保留版本、定位、适用条件及实际用途|
|审查自然语言证明|`proof-checker`|给真实定理与完整承重论证；取回具体义务、有效问题和审计范围，复核修正后的全局连接|
|讨论研究路线或进行有界审阅循环|`research-review`、`auto-review-loop`|给问题、现状、证据与待裁决分歧；按实际技能合同保留回应与改动，不用评分替代数学结论|
|实现、继续或审计 Lean|`lean-formalize`|给原题、实际定义、目标入口和当前连接；取回与原命题对齐的源码、执行证据及剩余义务|
|核对引用是否真有其文、是否支持用法|`citation-audit`、`citation-crosscheck`|给实际引用与使用处；区分书目字段核对与数学上满足被引定理的条件|
|把结果变成读者可用的展示|`render-html`、`paper-compile`|给已经确定的正文或工程；取回展示或编译产物，数学状态沿用原证据|
|分析测得的运行结果|`analyze-results`|给真实数据与明确问题；统计或性能判断不能直接改写普遍数学命题的证明状态|

这些名称是能力地图。调用前依当前宿主技能目录找到入口，核对其职责和依赖。
本版并没有因为列出它们就安装任何模型服务、自动生成 wiki、启动评审或构建 Lean。
当项目规定某个 reviewer 或特定验收方式时，把要求随任务传入；不从别的领域复制默认模型。

## 借鉴 auto-review-loop 的连续工作方式

该技能有用的地方，是把一次审阅放回持续研究中：读当前材料，收回真实意见，
判断哪些批评成立，完成修正或新的证据，再让审阅者检查仍有疑问的内容。
MathRSI 沿用这种连接，但数学中的“ready”不能由 ML 论文评分阈值定义。
定理是否得到证明，仍取决于原命题、推导、覆盖和所用信任基础。

恢复时先看上一次的具体阻塞和最新产物，而不是重放所有聊天。
若上轮已经闭合一个覆盖引理，本轮应使用它去构造实际输入或结束相应分支。
如果审阅指出真正错误，先修证明及受影响的下游调用；只承诺修正不足以送下一轮验收。
若意见不成立，给出原论证和精确反驳，使争议落到可检查的数学句子。

原始回应与作者处置分别保留。处置可以短而明确：哪一点成立、改了什么、证据在哪里，
或哪一点由既有假设消解。不要把审阅者的保留意见改写成赞同。
审阅调用失败或没读到关键附件，记录缺少了该范围的审阅；继续与它无关的已授权工作。
失败既不推翻已经检查的定理，也不满足用户要求的那次审阅。

从 ARIS 接回 MathRSI 的结果，应能回答：此次解决了哪个义务，实际检查了什么，
还有哪条从原输入到原结论的连接未闭合。无需把整套 reviewer 传输和状态字段复制进 base。

MathRSI 的五类交流信息可以自然容纳这些产物：任务说明原规格，
义务与连接说明实际数学链，行动提案说明调用哪项能力及预期信息，
结果与证据链接真实返回，验证能力说明该次检查足以支撑什么。
这是一种便于人和 agent 阅读的组织方法，不要求五份文件或统一 JSON。
若 helper 已能可靠完成机械工作，就直接复用它；
需要人或 agent 判断的数学问题，则保留推理空间，不用增加 Python 包装来假装自动裁决。

## 真正调用技能时，遵守它的完整合同

“借鉴一种做法”与“执行一个技能”分开处理。
若只是按照本页组织定向审阅，不宣称已经运行 `proof-checker` 或获得它的正式审计产物。
若用户点名执行该技能，则读取当前安装文件及本次必要引用，遵守其适用流程、输出和路由。
不能一边声称完成完整技能，一边跳过它要求的范围或伪造同名结果文件。

例如，安装版 `proof-orchestrator` 对新 run、手动 GPT Pro 包和可选外部调用有自己的约定。
需要它时让它管理相应 run，在本题主续接记录中链接该 run，避免再维护一份相互冲突的证明状态。
其手动交接能力不等于已经授权上传或付费调用；沿用用户当前任务授权和技能的实际调用合同。
普通跨轮研究若不需要这些专门行为，主技能中的精简续接说明就已足够。

`auto-review-loop` 本身已有内部循环。真正执行它时，使用其恢复与续接方法，
不在外面再包一个反复从顶部新建会话的计时循环。
由它返回的 score、verdict 和 acceptance 描述该次审阅流程；
MathRSI 仍把数学结论接回具体义务，不将“审阅结束”翻译成“原定理已证”。

宿主差异也要实事求是。Codex、Claude Code 等宿主的技能位置、委派入口和 MCP 名称可能不同。
先发现当前可用工具；若有服务但本轮工具未加载，按宿主说明解决入口，
不能仅凭项目记忆就声称已发起调用，或使用不存在的工具名写一段“执行记录”。
需要保持原生会话续接时，保存实际返回的会话标识和首轮固定选项。

## 以 research-wiki 保存知识，避免再造接受体系

已有 wiki 就继续使用。先读索引和与本次义务相关的知识页，再回到原证明或日志核查关键事实。
wiki 的价值在于保存一个结果为什么能用、失败为什么停止、满足什么新条件才值得重试，
不在于每个文件都生成一个节点。一次临时网络报错通常属于执行记录，
可迁移的配置修法或实际数学障碍才值得长期记忆。

实际使用 ARIS wiki 时，通过它的规范 helper 更新关系及派生索引，
不要手改自动生成的 Connections 或平行维护另一份 graph。
其 claim 状态属于证明轴，实验的 supports／invalidates 关系属于另一轴。
随机试验支持一个猜想，不应直接把 claim 改成 verified。
若本题只维护普通 Markdown 知识库，照样可记录精确的数学状态，
但不伪称该页已通过 ARIS 的 claim 登记或审计流程。

一个有用条目可以直接写成：“引理 L 适用于这些输入，证明与来源在这里；
旧参数的全部必要局部型已严格，新参数改变了顶点域，不能直接复用覆盖。”
这比堆积“模型建议使用三锁”等脱离条件的提示更能减少后续成本。

## 能力不可用时，完成相同的数学工作

缺少技能文件或 helper 时先说明具体缺项，然后选择人工等价操作。
这里的等价指完成有用的研究工作，不意味着获得那个技能的同名认证。
如果用户明确要求必须执行某个找不到的技能，按宿主约定查找后报告缺失，不能冒名继续。

|缺项|可继续的人工工作|需保留的准确说法|
|---|---|---|
|wiki helper|在现有 Markdown 记结论、条件、来源、失败域与重试理由|知识已记录，图和派生索引尚未由规范 helper 更新|
|证明审阅工具|逐条核对量词、引用条件、归约和边界，运行已有反例程序|本地核查范围；指定跨家族审阅若必需则仍待完成|
|Lean 工具链|先固定原题与声明，研究缺失数学，整理源码和最后错误|纸面或源码进展，不写成执行编译成功|
|专门续接技能|用当前工作区保留目标、已证结果、窄缺口和下一动作|普通续接记录，不虚构 proof-orchestrator 的 run 状态|
|HTML 渲染器|交付清楚的 Markdown 和原证据入口|数学交付与展示完成情况分别报告|

人工核查也应给出实质结果。工具不可用不需要先搭建一个替代平台，
更不应使所有独立推导停下等待；反过来，人工阅读不能冒充实际运行的独核或形式验证。
用户要求的最终证据若确实依赖缺失能力，完成其余部分并精确指出剩余项目。

## 一个实际组合方式

假设工作区已经有一个局部概率引理和未完成的分类。
先从 wiki 取出旧引理及适用预算，借助插件重算新参数的必要域，
然后让 worker 完成一个明确有限域的精确计算，同时主代理证明真实超图怎样进入该域。
表格回来就读取最紧行和计算范围，并将计算用于实际 caller；不用等其他并行材料全部交付。

若关键疑问是两个规范化能否同时成立，定向审阅应提供同一原对象、两个变换及其作用，
请 reviewer 证明组合保真或给出漏解见证。这里 `research-review` 可承担讨论，
已有完整论文证明需要系统审计时再使用 `proof-checker`。
如果 Lean 接口能够低成本暴露隐藏前提，可由 `lean-formalize` 提前写真实调用，
而不是先形式化整张表之后才发现原输入没有所需证书。

完成时把已闭合的数学链写入正文，把运行命令、复算范围和审阅记录留在相应证据入口。
读者需要离线单卷时再调用 `render-html`。数学审阅与展示保真是两个具体问题，
二者都不由“文件已生成”自动满足。
